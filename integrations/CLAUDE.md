# integrations/
> L2 | Parent: ../CLAUDE.md

Code that runs inside another program, not inside `rex do`. Each file talks to the engine only through files or the `rex` command.

rex_revive.lua: Rex config actions. install.sh fills @REX@, @SCRIPT@, and @LOG@ (the watcher's log; empty on Linux, where it is the journal) and copies it to ~/.config/rex/. Every run it starts gets `log=@LOG@`, as nobody reads its stdout. `revive_choose` has two callers. From the palette, it runs `mode=choices`, asks with `rex.ui.pick{multiple=true}`, then starts `mode=restore only=…`. From the watcher after a restart, `rex do revive_choose --args {items}` (chats and programs) asks in every connected Rex app and returns `{keys}` only when someone pressed Reopen. `rex.ui.pick` works only in an action's own body: never in pcall, rex.on, or rex.invoke. Rex requires a `title` on every action and has no hidden action, so the watcher reuses this one. `row` draws a chat (its title from lib/titles, else its folder; `detail` how long ago it was active) or a program ("typed, not run"); it sets `selected` from revive.lua's `ticked`, and only in a multiple pick, as Rex allows it nowhere else. In a multiple pick ⌘↩ answers, so the filter's placeholder says so. `revive_reopen_closed` runs `mode=closed` and asks with a single pick; `revive_reopen_last` reopens the newest. Both start `mode=reopen session=<ctx.session_id>`, so the tab opens where the person is. ⇧⌘T is bound to `revive_reopen_last` only when `rex.bindings` shows no earlier binding of it. `revive_preview` runs `mode=preview` and lists each tab with what it would type (an agent's resume command; else "typed, not run"); picking a row starts `mode=focus`. `revive_reopen_earlier` runs `mode=history` (rows with the `clock` icon), then `mode=choices from=<id>`, then starts `mode=reopen from=<id> only=…`. `revive_settings` asks with a single pick whether to ask after a restart and writes it with `mode=settings ask=…`. Every action has a `description` for the palette.
agent-hook.sh: the SessionStart hook behind Gemini CLI's and Droid's pid records (install.sh --gemini, --droid add it to their settings.json). Reads session_id from the hook JSON on stdin, takes as the agent the nearest ancestor with a command-line word named like it (Gemini runs as node .../gemini.js), and writes {pid, sessionId, startedAt from ps etime} to ~/.gemini/rex-revive or ~/.factory/rex-revive; drops records of dead pids. Prints nothing, always exits 0.
amp-rex-revive.ts: the amp plugin behind amp's pid records (install.sh --amp copies it to ~/.config/amp/plugins/rex-revive.ts). Its first line is the marker amp requires. On session.start and agent.start (a thread change shows there first) it writes {pid, sessionId = thread ID, startedAt} to ~/.local/share/amp/rex-revive; removes it on exit. amp runs plugins in a child process (amp .../plugin-runtime.ts), so pid is the parent, the amp Rex sees in the tab, and startedAt is that process's start from ps; the plugin's own pid would match nothing. Checked against real amp with `amp plugins exec`.
opencode-rex-revive.js: the opencode TUI plugin behind opencode's pid records (install.sh --opencode copies it to ~/.config/opencode/plugins/rex-revive/tui.js; opencode 2.3.2 loads a TUI plugin from each such folder with a tui.js, and `opencode plugin list` shows them). Default export `{id, setup(api)}`. TUI plugins run in the TUI process itself, so `process.pid` is the opencode in the tab (unlike amp). Every second it reads `api.ui.router.current()`; on a session route it writes {pid, sessionId (ses_…, a subagent's mapped to its root by api.data.session.root), startedAt}; on any other route, and in setup's cleanup, it removes the file. Server plugins can't do this: they run in the shared `opencode serve` process, and no event tells which session a TUI shows. Checked against real opencode 2.3.2 in a pseudo-terminal: pid and startedAt match ps; SIGHUP removes the record.
pi-rex-revive.ts: the pi extension behind pi's pid records. On session_start (UI sessions only) it writes ~/.pi/agent/rex-revive/<pid>.json with sessionId, startedAt from process.uptime, and pi's argv, which pi hides from ps; it removes the file on quit. No network, no output.
